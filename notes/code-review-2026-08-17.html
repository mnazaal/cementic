1. Fixes that stopped one layer short

1.1 status -c <unknown> --json still exits 0 with the zero-filled report the fix eliminated in human mode. contract silent

cli.py:1146-1158 (JSON branch returns early) vs cli.py:1206-1207 (_require_known_collection, human path only) · _print_status_json named-collection branch cli.py:901-921

1.2 Scan-time symlinks are still dropped in complete silence — the skip-recording fix covers only live events. silent

source_watcher.py:394-399 (_scan_existing filters not file_path.is_symlink() before _on_file_detected) vs source_watcher.py:458-481 (record_skipped lives in _register_document)

e889aa1's own motivating example — "a collection that dropped a directory of symlinks still reported 100%" — is the scan case: existing symlinks are seen by _scan_existing, which filters them out before the recording path, so no counter, no path, not even a log line. Only a symlink arriving later via inotify is recorded. A dangling symlink also fails is_file() and vanishes the same way. Two more counters bypass the list: _on_walk_error (source_watcher.py:380 — one unreadable directory of arbitrarily many files counts as one "file") and the registration-exception path (source_watcher.py:406) increment failed without a record_skipped entry, so the headline count can exceed what --verbose can name and the "(showing the N most recent of M)" footer implies truncation that never happened. Fix: drop the scan-side symlink filter and let _register_document classify (it already does), and record a path string from the other two sites.

1.3 cementic stop still misreports EPERM-alive workers — and now destroys the recovery state too. correctness

cli.py:1255-1280 (signal loop) · supervisor.py:77-82 (the fix)

The fourth review's §2.5 fix landed in is_pid_running (EPERM → alive), but the stop path re-creates the defect one call later: _is_managed_proc_alive now correctly says True, then os.kill(pid, 15) raises PermissionError, the except (ProcessLookupError, OSError): continue at cli.py:1265-1266 drops the pid, signaled_pids stays empty, remaining is empty — and the not remaining branch prints "no running processes found; cleared stale state", exits 0, unlinks supervisor.json and calls _clear_worker_state_files(), which erases the per-worker pid records that _worker_processes_from_state_files() exists to recover from. Same scenario the fix commit cited (workers under another uid): stop reports success, both workers keep indexing, and every trace of them is now gone. Fix: split PermissionError out of the kill's except; report un-signalable pids and exit 1 without clearing state. (Nit at the same lines: ProcessLookupError is a subclass of OSError, so the two-tuple is redundant.)

2. New correctness and silent-failure findings — worker & database layer

2.1 collection remove against a running worker: the worker idles forever and the watcher resurrects the collection. correctness silent

cli.py:1389+ (no running-worker guard) · pipeline_worker.py:400-403 (revision_id cached at startup; steps session.get(...) is None → return False) · source_watcher.py:497-522 (keeps registering)

Found independently by two reviewers. remove deletes the collection's revision rows; the running pipeline worker's every step then silently no-ops (it never re-runs _ensure_target_revision), while the live watcher re-registers files into the removed collection. Observable: "status: deleted", then collection list shows the collection back with fresh documents and status shows both workers "running" while nothing is ever indexed again. Fix: refuse removal of the supervisor's active collection while workers are alive (probe the worker's advisory lock or the supervisor record), or make the worker re-resolve a vanished revision.

2.2 SET maintenance_work_mem leaks into the connection pool; the code's own comment claims the opposite. correctness

db.py:427 (session-level SET) · db.py:422-426 (comment: "the connection is discarded afterwards")

with engine.connect() returns the connection to the pool, and SQLAlchemy's reset-on-return only issues ROLLBACK — session GUCs survive. Any later checkout of that pooled connection (a long-lived worker engine) carries 2GB maintenance_work_mem the operator never asked to persist. The CREATE INDEX commits in the same transaction, so SET LOCAL is a strict fix and makes the comment true.

2.3 A post-commit cleanup failure makes a successful promote report as failed. contract

collections.py:291-292 (cleanup after session.commit()) · cli.py promote handler prints "collection promote failed", exit 1

If remove_artifacts/drop_orphan_vector_tables raise after the commit, the promotion is durable but the CLI reports failure. collection remove guards this exact case ("collection deleted but cleanup failed"); promote needs the same warning-not-failure guard.

2.4 skipped_files is never reset, so every restart shows the previous run's skips against this run's zeroed counter. correctness

state.py:177-189 (update() has no skipped_files parameter) · source_watcher.py:246-247 (resets only the counters) · cli.py:715-719 (the of-N footer then can't reconcile)

After stop && start, status --verbose/--json shows failed=0 beside a populated skip list carried over from the prior run — stale paths presented as current. Fix: add skipped_files to update() and reset it in start().

2.5 A NULL source_content_hash on a terminal ChunkedDocument wedges the revision in building forever. correctness

pipeline_worker.py:615 (claim uses !=, SQL-NULL falsy) vs pipeline_worker.py:224-227 (purge handles .is_(None)) · revisions.py:108 (chunked_scope requires hash equality) · pipeline_worker.py:687/700 (status set unconditionally, hash only if extracted is not None)

Reachable when an ExtractedDocument vanishes mid-flight (concurrent prune from another process's promote) and for legacy pre-column rows. Fix: add ChunkedDocument.source_content_hash.is_(None) to the claim's or_, mirroring the purge.

2.6 The persist-time whitespace-chunk filter reintroduces the chunk_index/total_chunks disagreement the same session fixed inside chunk_text. correctness

pipeline_worker.py:668 (filter keeps original indices) · pipeline_worker.py:699 (total_chunks = len(chunk_items))

2.7 Search's revision choice still depends on whether you named the collection — second independent derivation, still unfixed. correctness carry

search.py:334-345 (-c fallback: newest in-flight by id — building beats ready) vs search.py:133-146 (_searchable_revisions: ready ranks above building, pinned by test_search.py:296)

Was §2.10 in the fourth review; not in the fixed set and not in the deferred list, so it is now a twice-derived open item. 2.8 Concurrency edges around promote unverified

revisions.py:288-298 · db.py:292-302 · collections.py:254-293

  • Two concurrent promotes can mint two active revisions — no partial unique index (confirmed absent on the live DB's pg_indexes), no row lock; READ COMMITTED lets each retire-UPDATE miss the other's new active row. Self-heals on the next promote and readers pick newest-id, but collection list/search silently prefer one. One-line fix: CREATE UNIQUE INDEX ... ON pipeline_revisions (collection) WHERE status = 'active'.
  • Promote validates status on a stale ORM object (revisions.py:288-289): a worker's concurrent _supersede_other_in_flight_revisions can commit superseded on the same row, and promote's attribute-write clobbers it to active, publishing an abandoned build. Fix: UPDATE ... WHERE status='ready' + rowcount, or with_for_update().

Both are reasoned from READ COMMITTED semantics, not executed.

2.9 Smaller worker/watcher items

  • A partially-missing watch directory poisons fatal_reason (source_watcher.py:292-293 · runner.py:92-93): _fatal is recorded per missing dir but the watcher proceeds if any root is valid — then runs for days and exits 1 on a clean shutdown; the missing dir itself reaches no counter or skip record. Separate "warn and record" from "abort".
  • Watcher stop() ordering (source_watcher.py:561-565): cancel_all() runs before observer.stop()/join(), so the still-live observer can arm debounce timers that fire after shutdown and write state after STOPPED. Swap the order.
  • Extract/chunk steps have no transient-vs-permanent distinction (pipeline_worker.py:548-556, 657-675): a full disk or NFS blip stamps documents terminally failed (recovered only by the next start's requeue), while the embed step carefully distinguishes retryable errors. Related: _embed_individually stamps rows failing for their own reason with the batch error string (pipeline_worker.py:896-902).
  • Directory-level moves are invisible until restart (source_watcher.py:158-159, 168-169) unverified: mv watched/docs /elsewhere leaves dead paths searchable until the next restart's reconcile; a directory moved in indexes nothing until the next scan. Rests on watchdog's inotify emitter behavior for cross-boundary moves.
  • Nested-root ignore edge (source_watcher.py:108-113): a root explicitly watched inside an ignored dirname of a broader root has its live events dropped while the scan indexes it.
