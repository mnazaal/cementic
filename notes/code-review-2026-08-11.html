New — blocking / destructive

N1. cementic init postgres DIR --force recursively deletes any directory two independent derivations
cli.py:286-290 · tests/unit/test_cli.py:116 locks the behavior in

if directory.exists() and force: shutil.rmtree(directory) — no check that the target is (or contains) a previously generated setup. cementic init postgres ~ --force or … . --force irreversibly deletes the tree before writing a handful of template files. Found independently by both the CLI reviewer and the packaging reviewer. Related: an existing file argument tracebacks (directory.iterdir() → NotADirectoryError).

Fix: refuse --force unless the directory looks like a prior generated setup (e.g. contains compose.yml + Containerfile), or replace only the template filenames; reject non-directory targets with a message.

New — wrong results / wrong publishes

N2. A brand-new collection's revision goes ready before anything is indexed
pipeline_worker.py:151-157 (probe: complete at all-zero counts), :791-800 · revisions.py:221-225

_revision_is_complete is trivially true with zero documents (0+0==0 at every stage). On first cementic start both workers spawn together; the pipeline worker's first loop pass usually beats the watcher's registration of even one file, so the revision flips building → ready immediately, and nothing ever demotes it. collection promote then publishes an empty index with zero failures reported. Sharpened form of prior H2 (the one-way latch): ready is not merely sticky, it is reachable vacuously.

Fix: require counts.documents > 0 in _revision_is_complete — and (H2's fix) re-check completeness at promote time.

N3. A worker restart launders failures past the promote gate
revisions.py:228-274 (requeue_interrupted_artifacts, run on every start via pipeline_worker.py:338) · collections.py:223-224

The promote gate blocks only on revision_failure_total(counts) > 0. Requeue flips every failed row to pending on each cementic start, so a promote that was correctly blocked_by_failures succeeds without --force if issued after a restart and before the retries finish — pending rows count as neither failed nor done. Same missing check as H2/N2: the gate never asks _revision_is_complete.

Fix: one fix closes N2, N3 and H2 — promote_ready_revision must require completeness (report an "incomplete" outcome with pending counts) in addition to the failure-count gate.

N4. Changing index.method on a built system is silently ignored forever
revisions.py:319-338 (sole caller: pipeline_worker.py:798, inside a status == "building" guard at :794) · db.py:411-417 · search.py:131-139

The method-switch DROP/CREATE in ensure_embedding_ann_index is unreachable in the very scenario it exists for: a steady-state ready/active revision never re-enters building, and ensure_revision_ann_index has no other caller. Search then deliberately tunes for "the index that actually exists", so the user gets no signal that index.method is dead config. PLAN.md's claim that the method "takes effect on the next rebuild" has no trigger behind it — TODO.md's proposed collection reindex would be that trigger and should be promoted from roadmap to fix.

Fix: also reconcile the index at promote time or worker startup for the target revision regardless of status (it never re-embeds, so this is cheap), or land collection reindex.

N5. Raising llama_cpp.n_ctx is a no-op: the daemon never passes --n_batch
embedding_runtime.py:570-590 · vendored llama_cpp: Llama.embed caps input at n_batch; server default n_batch=512

The server truncates every embedding input at min(n_ctx, n_batch) tokens, and n_batch stays at its 512 default because the spawn command never sets it. So the documented mitigation for the truncation findings (C1.1 queries, chunk-size fit) — "raise n_ctx and re-measure" — silently does nothing above 512. This also bounds C1.1: the real silent-truncation threshold is ~512 model tokens regardless of config.

Fix: pass --n_batch/--n_ubatch = n_ctx when spawning and include them in the runtime fingerprint.

N6. A model-migration build breaks unfiltered search of every collection
search.py:108-113, 238-244

_load_searchable_revisions(None) includes building revisions. Start indexing any collection with a different embedding model and plain cementic search fails with "Selected collections use different active embedding models" for the whole duration of the build — every previously searchable collection becomes unsearchable, and the error names no collection and says "active" about a building one. Sharpens the prior M-item (which covered two collections with different active models).

Fix: on the unfiltered path, restrict to the active-model majority and note the excluded collections on stderr; name the offenders in the filtered-path error.

New — silent failures & misleading diagnostics

N7. Malformed CEMENTIC_DB_URL tracebacks in the three commands meant to explain it
doctor.py:98 (renders the URL before the try block) · bootstrap.py:91-93 (re-evaluates self.config.database.url inside the f-string of the friendly RuntimeError) · cli.py:1422 (Searcher(_get_config()) constructed outside the try)

Probe-confirmed with CEMENTIC_DB_URL="not a url": status --doctor, start, and search all show a raw ArgumentError traceback. The bootstrap case is the sharpest: the parse error is raised while formatting the "Cannot use Postgres at …" message written for exactly this situation.

Fix: validate/parse the URL once in a DatabaseConfig validator so it fails as a config error with one line.

N8. cementic stop exits 0 when it failed to stop anything
cli.py:1147-1151 (timeout path), :1129-1136 (unkillable-after---force path)

Both paths print the failure and return → exit 0. cementic stop && cementic start proceeds and then contradicts itself with "already running".

Fix: raise typer.Exit(1) on both paths where processes remain.

N9. Doctor passes configs that start is guaranteed to reject
config.py:301-304 (no validator on embedding_provider; contrast IndexConfig.method) · doctor.py:130-147 vs bootstrap.py:122-130

(a) embedding_provider = "llama_cpp" (underscore typo) loads fine and doctor runs the llama-cpp checks anyway; first start dies with "Unsupported embedding provider". (b) For a model path outside the data dir with auto_download_llama_model=true, doctor reports "missing; cementic will download it automatically" — but _ensure_llama_model refuses to download outside the data dir, so start fails while doctor says ok.

Fix: validate the provider against the registry; replicate the containment check in doctor's model check.

N10. First-run model-download failures are raw tracebacks
cli.py:848-854, 1164-1168 (both call sites catch only RuntimeError) · bootstrap.py:144-159 (raises requests errors and OSError)

No network on the machine doing the initial fetch — the most common first-run failure — is a traceback instead of "Bootstrap failed: …". Related: two processes bootstrapping simultaneously share the one fixed .{name}.tmp download path (bootstrap.py:140-162); interleaved writes are normally caught by the checksum, but with verification off (custom URL, the documented opt-out) a corrupted GGUF installs silently.

Fix: wrap download failures in RuntimeError inside _ensure_llama_model; use tempfile.mkstemp or the existing filelock for the download.

N11. An unreadable subtree is treated as deleted
source_watcher.py:273-286

_reconcile_deletions tests Path(...).exists(), which returns False on PermissionError, not just absence. A chmod mishap or NFS/automount hiccup at startup marks every document under it deleted (+ file_hash=None), dropping them from search until a later restart's rescan.

Fix: distinguish FileNotFoundError from other OSErrors via path.stat().

N12. Stop-side kill escalation is PID-only, bypassing the start-token machinery
supervisor.py:157-183 (wait_for_exit, force_kill) · used at cli.py:1109, 1123

The initial SIGTERM is token-checked, but the wait-and-escalate helpers use bare is_pid_running/os.kill(pid, 9). A worker that dies inside the 5-10s grace window while its PID is recycled means waiting on — and force-killing — a stranger's process. Narrow race; it is exactly the hole the token exists to close.

Fix: thread (pid, start_token) pairs through both helpers.

N13. Health fallback reports "healthy" for a daemon serving the wrong model
status_service.py:408-410

health_check() correctly returns False when /v1/models answers with a non-matching fingerprint ("genuine config change, not busyness") — then the pid-based fallback flips it back to healthy. The fallback's own justification covers only the busy-vs-down ambiguity, i.e. the case where the HTTP probe got no answer.

Fix: apply the fallback only when the probe got no response (thread the tri-state through); part of the "busy vs dead" consolidation the prior note lists.

N14. An embedding dimension pgvector cannot index passes validation
vector_store.py:16 (_MAX_EMBEDDING_DIM = 8192; pgvector hnsw caps at 2000)

A 2001-8192-dim model embeds the entire corpus successfully, then fails at ANN-index creation inside _mark_revision_ready_if_complete — the revision loops in building with a recurring error after all the expensive work is done.

Fix: validate against the per-method indexable limit before embedding starts.

N15. Fresh-install status exits 1 on the state its own comment calls normal
cli.py:483-492 (docstring: "normal pre-first-run state, not a fault") vs :1053-1055

Missing schema prints the friendly "nothing indexed yet" hint and then exits 1 via the generic error path. Related low-severity inconsistency: collection remove of an unknown name exits 0 ("not found"), while search of an unknown collection exits 1 — scripts cannot rely on either convention.

N16. Prune leaves stale chunk_embeddings rows when only the embedding model changed
revisions.py:399-408

The explicit ChunkEmbedding delete is scoped to chunks under removed chunk profiles; in the common model-swap case (chunk profile kept), the dropped embedding profile's rows survive indefinitely — on top of the already-known orphaned vector table + ANN index (prior M-item). Where the explicit delete does apply it is redundant with the FK cascade.

Fix: delete by embedding_profile_id ∉ keep-set on the collection's chunks, and drop vector tables for profiles no longer referenced by any revision.

N17. CI marker holes: a compose-launching test in the no-DB job; the smoke test in no job at all
tests/integration/test_db_isolation.py:32 (no pg marker, uses pg_config) · tests/integration/test_smoke.py (no marker, self-skips) · ci.yml:53, 76

Once the lockfile lands (B1), CI still is not what it appears: the "not pg" integration job selects test_pg_config_fixture_points_at_the_test_database, whose session fixture runs docker compose up — a 30-60 minute from-source cargo/pgrx build on ubuntu-latest — in the job designed to need no database. And the only full build→promote→search smoke test carries no pg marker, so the -m pg job excludes it and the not pg job skips it: zero CI coverage, silently.

Fix: pytestmark = pytest.mark.pg in both modules.
