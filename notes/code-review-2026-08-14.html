cementic — fourth comprehensive code review

2026-08-14 · CLI API first, then every path it reaches · read-only, git status clean throughout · six parallel reviewers over disjoint subsystems, plus direct black-box exercise of the CLI against a live Postgres and a live embedding daemon. Every finding promoted here was spot-verified in the parent session; findings I could not verify are marked unverified.

Baseline. ruff check src/ tests/ clean, mypy src/ clean, pytest 864 passed in 31.3s (744 unit + 49 pg-marked + the rest), no warnings. The tree is healthy by every check it runs on itself. Everything below sits in the gap between "the checks pass" and "the behaviour is right" — which is why most of it is invisible to the suite.

1. Headline: 30% of every full-size chunk is silently discarded before embedding

Documents are embedded past the model's context window and truncated without error. correctnesssilent

config.py:446-456 · chunk.py:33 · scripts/measure_chunk_context_fit.py:78

Shipped defaults are pipeline.chunk_size = 512 (counted in cl100k_base tokens) against llama_cpp.n_ctx = 512 (counted in the model's own XLM-RoBERTa tokenizer). The two tokenizers do not agree, and chunk.py has no context check of any kind. search.py:41-56 guards queries against exactly this and explains why — "The server truncates over-long input silently" — but nothing guards documents, on either write path (pipeline_worker.py:742, cli.py:1757).

Measured directly against the running daemon at shipped defaults, using the same tail-sensitivity test search.py describes — embed chunk + " ZEBRA" and chunk + " QUANTUM" and compare:

chunk length:        3675 chars (512 cl100k tokens)
full-size chunk:     vectors identical? True    cosine = 1.000000000
short control:       vectors identical? False   cosine = 0.843376816
effective cutoff:    ~2568 chars (359 cl100k tokens)
SILENTLY DISCARDED:  30% of each full-size chunk

A bit-identical vector regardless of the tail is proof the tail never reached the model. The last ~30% of every full-size chunk is unsearchable, and the stored chunk text disagrees with the vector that indexes it. No error, no log line, no counter.

Why the existing measurement says otherwise

config.py:449-455 asserts the opposite, and cites a measurement: "full chunks embed without error and remain tail-sensitive, so nothing is silently truncated. Re-measure before raising this or lowering n_ctx." That measurement never tested a full chunk. scripts/measure_chunk_context_fit.py:78 does:

head = chunk[: int(len(chunk) * 0.75)]

…then embeds head + marker while printing the full chunk's token_count next to an "ok (tail affects the vector)" verdict. It tests 75% of a chunk and reports it as 100%. The untested last quarter is precisely where overflow begins. Changing that one literal to 1.0 and rerunning the script's own four cases:

case          tokens   chars  verdict                        case          tokens   chars  verdict
english          512    2343  ok (tail affects the vector)   english          512    2343  TRUNCATED (tail ignored)
cjk              512     432  ok (tail affects the vector)   cjk              512     432  ok (tail affects the vector)
code             512    1356  ok (tail affects the vector)   code             512    1356  TRUNCATED (tail ignored)
diacritics       512     795  ok (tail affects the vector)   diacritics       512     795  ok (tail affects the vector)

All cases fit: full chunks embed intact.                     2 case(s) failed: chunk_size and n_ctx are not compatible.
        ^ as shipped (0.75)                                          ^ same script at full length (1.0)

English and source code — the two content types this corpus is mostly made of — fail. CJK and diacritics pass because they produce far fewer characters per cl100k token, so their 512-token chunks are short enough to fit. The green result is an artifact of the harness, not of the configuration.

Consequence: every collection indexed to date has ~30% of each full-size English chunk missing from its vectors. Fixing the setting requires a full re-embed, so this is worth settling before the corpus grows further. The fix is a real measurement (drop the 0.75), then either lower chunk_size to what actually fits or raise n_ctx, plus a hard check at the embed call so overflow can never again be silent.

2. Silent failures — the user sees success, something else happened

2.1 Files the watcher drops never appear in any status the CLI points you at. silent

source_watcher.py:459-480, :375-380 · cli.py:723-731

Every rejection path in _register_document — symlink, path outside the watched roots, stat failure, file over 512 MiB — and the os.walk onerror handler records the loss only as increment(failed=1) plus a line in a log file. Those files never become SourceDocument rows, so they are absent from every denominator downstream. _print_collection_detail's failures line reads only the pipeline-stage counters (extracted_failed, chunked_failed, failed_embeddings) — never the watcher's.

Watch 500 .md files of which 40 are symlinks: the watcher registers 460, and cementic status -c prints extracted 460/460 (100.0%) with no failures line at all. collection promote then succeeds, because revision_failure_total also counts only pipeline artifacts. The user gets a complete, promotable, 100% collection that is missing 40 documents, and the only trace is a number behind --verbose with no paths attached.

2.2 A typo'd collection name is invisible whenever any other collection returns a hit. silent

cli.py:1613-1616

unknown = searcher.unsearchable_collections(filters) if not results and filters else []

The "no indexed revision for X" diagnostic is computed only when the entire result set is empty. Verified against the live database:

$ cementic search hello -c nope            → "no results" + note about `nope`   [exit 0]
$ cementic search hello -c test -c nope    → 2 results, no mention of `nope`     [exit 0]

Half the query was silently dropped. In --json mode this is worse: the JSONL stream is well-formed and the exit code is 0, so a script cannot detect it at all.

2.3 A failed re-extraction leaves the old content searchable indefinitely. correctnesssilent

pipeline_worker.py:551-552

if content_hash is not None and previous_content_hash != content_hash:
    _purge_superseded_chunks(session, extracted.id, content_hash)

On failure content_hash is None (:532), so the purge is skipped while source_file_hash is updated to the new file. Search applies no freshness filter — knn_sql filters on collection and profile ids only, and search.py:246-255 documents the freshness join as deliberately removed. So replacing an indexed report.pdf with a corrupt or encrypted one leaves the v1 text being returned under the current path forever. status -c shows failures extract=1 and nothing that suggests searches are serving replaced content.

2.4 A malformed config file is ignored with one stderr line, and cementic runs on defaults. silent

config.py:275-284, :791-798

load_config_file() swallows TOMLDecodeError/OSError and returns {}, so config_file_problems() finds nothing and Config() is built from defaults. Verified — a file whose first line is malformed but which then sets a valid [database] name = "MYCUSTOMDB":

$ cementic config show          → warning: ignoring malformed config file …
                                  "name": "cementic"     ← the user's setting is gone
                                  [exit 0]

Every other config error class is a hard exit-1 error — bad value, unknown key, missing $CEMENTIC_CONFIG. The one that discards the whole file is the lenient one. Under cementic start that single warning scrolls past and the corpus is indexed against a different database with different chunk settings. config_file_error() (config.py:109) detects this correctly but is wired only into status --doctor.

2.5 cementic stop can report success while the workers keep running. correctness

supervisor.py:73-76

try:
    os.kill(pid, 0)
except OSError:
    return False        # ← folds EPERM ("exists, not yours") into "not running"

force_kill a hundred lines below gets this right — except OSError: remaining.append(pid) # e.g. EPERM: alive but not ours to kill. Where the two disagree, is_pid_running wins the stop path: workers started under another uid (sudo, a service account, a user namespace) are reported dead, stop prints "no running processes found; cleared stale state" and exits 0, and status agrees — while both workers keep indexing. One line: split ProcessLookupError (False) from PermissionError (True).

2.6 cementic start reports success ~60× earlier than startup can fail.

cli.py:374 (_STARTUP_GRACE_SECONDS = 2.0) · config.py:415

PipelineWorker.start calls describe(), which autostarts the llama.cpp daemon and waits out daemon_start_timeout_seconds — default 120s. A corrupt GGUF, a bound port, or too high n_gpu_layers kills the worker around t=120s; cementic start printed "Started cementic in background" and both PIDs at t=2s and exited 0. The failure reason goes to stderr → the background log, whose path is printed only in the other branch (cli.py:994) and appears nowhere in status or doctor. The user sees workers partial in yellow with last_error: None.

2.7 cementic embed fabricates embeddings for absent or null content. silent

cli.py:1757

texts = [provider.format_document(str(rec.get("content", ""))) for rec in batch]

Verified end to end:

stdin linewhat gets embeddedoutput
{"index":0,"text":"hello world"} (no content)the empty stringa plausible 768-dim vector, exit 0
{"index":0,"content":null}the literal string "None"a plausible 768-dim vector, exit 0
{"index":0,"content":12345}"12345"vector, exit 0

str(None) → "None" is the sharp edge: a null content field is embedded as a four-letter English word. A missing/null content should be an error, not a vector.

2.8 An empty or whitespace-only query returns confident, meaningless results. silent

search.py:177-180 · cli.py:1577

search() bounds top_k and the maximum query length, but never rejects an empty one:

$ cementic search "" -n 2      → 2 ranked results, exit 0
$ cementic search "   " -n 2   → the same 2 results, exit 0

These are the nearest neighbours of the embedding of nothing. Ranked output with scores is exactly the wrong signal for that input.

2.9 search silently serves unpromoted revisions, and the docs contradict themselves about it.

search.py:301-334 · README.md:5, 111, 157, 326 vs :179-180

Observed on the live database: collection list reports test with active=- and only a ready revision, and cementic search nonetheless returns ranked results from it — with nothing in the output indicating the index has never been promoted. The fallback is intentional (_load_searchable_revisions falls back to ready/building) and README:179-180 documents it, but README:5, :111, :157 and :326 all state the opposite ("searches only the active revision"), as do search.py's own module and class docstrings.

Two consequences beyond the doc drift. First, a building revision is searchable, so results can come from a 2%-complete index with no marker distinguishing them from a finished one. Second, it partly defeats promote: the gate that refuses to publish a revision with failed documents is bypassed, because search reads the unpromoted revision anyway.

2.10 The revision search picks depends on whether you named the collection.

search.py:315-323 vs :127-140

The -c path takes status.in_(BUILDING_STATUSES) ordered by id.desc() — newest wins, so building beats ready. The no-filter path uses _searchable_revisions, whose status_rank = {"active": 3, "ready": 2, "building": 1} prefers ready over building regardless of id. With a fully-built ready revision 5 and a 2%-complete building revision 7, cementic search "q" -c docs reads revision 7 and cementic search "q" reads revision 5 — same database, same instant, different answers, no diagnostic either way.

3. Correctness bugs

3.1 reindex --force commits the index drop in its own transaction.

collections.py:316-320

if force and previous_method is not None:
    with engine.begin() as conn:                      # ← commits the DROP
        conn.execute(text(f"DROP INDEX IF EXISTS {vector_index_name(profile_id)}"))
ensure_revision_ann_index(session, revision, config)  # ← separate connection

db.py:420-427 does the equivalent method-switch drop+create on one connection with a single commit, so a failed build rolls the drop back. The --force path breaks that. Any failure of the rebuild — Ctrl-C, statement timeout, disk full, or a >2000-dim profile that HNSW rejects at execution time — leaves the collection with no ANN index at all, permanently. Searches still succeed via sequential scan and search.py:231-237 falls back to the configured method for tuning, so nothing anywhere warns.

3.2 The schema migration inside search() is never committed.

search.py:224-228 — no commit/rollback anywhere in the file (verified by grep)

ensure_vector_table_schema runs ALTER TABLE ADD COLUMN ×3, a full-table backfill UPDATE, a DELETE and three SET NOT NULL — inside a session whose context manager closes without committing, i.e. rolls back. On a database written by an older cementic, every search re-runs the whole backfill over every vector row, holds ACCESS EXCLUSIVE on the vector table for the duration, and throws the work away. It never converges. The worker path (pipeline_worker.py:788) does commit, so the comment justifying the call — "Idempotent, and a catalog lookup once done" — is true there and false here. unverified — the absence of the commit is verified by grep; the runtime cost is reasoned from SQLAlchemy Session.close() semantics, not executed against a pre-migration database.

3.3 Chunk indices are non-contiguous at small chunk sizes.

chunk.py:84-91 — chunk_index += 1 runs every iteration; the append is conditional

chunk_text("😀"*20, chunk_size=1, chunk_overlap=0)
  → 20 chunks, indices [0, 2, 4, 6, 8, 10, …, 38]     (verified)

ChunkedDocument.total_chunks = len(chunk_items) then bears no relation to max(chunk_index), and cementic chunk --chunk-size 2 emits JSONL whose index field skips values. Reachable from any chunk_size ≤ ~3, which both the config (ge=1) and the flag (min=1) accept. Existing tests assert contiguity on ASCII only, where the boundary-widening never empties a slice.

3.4 Two config file errors produce raw multi-screen tracebacks.

config.py:124, :276 (UnicodeDecodeError) · config.py:576, :637 (SettingsError)

Both verified through the CLI:

  • A non-UTF-8 config file → UnicodeDecodeError. Both tomllib.load sites catch TOMLDecodeError and OSError only; UnicodeDecodeError is a ValueError. config_file_error() has the same hole, so status --doctor — the command that exists to explain this — crashes too.
  • CEMENTIC_EXTRACT_BACKENDS=pdf=pymupdf4llm → pydantic_settings.SettingsError, whose MRO is (SettingsError, ValueError, Exception), so _get_config()'s except ValidationError misses it. Complex-typed fields are JSON-parsed by the env source; only {"pdf":"pymupdf4llm"} works, and that is documented nowhere while README:262 promises "Every setting also has a CEMENTIC_* environment variable".

3.5 Smaller correctness items

  • config.py:66 — resolve_config_path() does Path(explicit) with no .expanduser(), while config_path_error() (:154) does. So CEMENTIC_CONFIG=~/cfg.toml passes the guard and is then never found: the request is silently ignored and config path prints the fallback. With a ./cementic.toml present, a different file is loaded.
  • config.py:346-350 — url_override in the file plus CEMENTIC_DB_URL in the environment is an extra_forbidden error, not an override, violating documented precedence for that one setting. The message is self-contradicting: "[database] url_override: Extra inputs are not permitted — did you mean 'url_override'?"
  • config.py:208-216 — a known section name whose value is not a table (database = "myhost" instead of [database]) is dropped with no problem reported at all.
  • config.py:662-665 — poll_interval has no lower bound (its neighbour batch_size has ge=1, le=128). 0 or a negative value makes Event.wait() return immediately, so the worker busy-polls Postgres — indistinguishable from healthy idle.
  • config.py:531-542 — build_memory's grammar admits "0" and "999999999999GB", which PostgreSQL rejects at index-build time, i.e. after the whole corpus is embedded. (Injection itself is genuinely prevented — only digits, whitespace and unit letters are admitted.)
  • db.py:314-316 — connect_args={"connect_timeout": 5} is applied to any URL, so a non-Postgres CEMENTIC_DB_URL dies at connect with a raw TypeError; and the gssencmode=disable workaround is keyed on startswith("postgresql://"), so it silently does not apply to postgresql+psycopg2://.
  • supervisor.py:144-154 — spawn_detached never redirects stdin, so cementic start < file leaves the detached workers holding the pipe's read end open. start_new_session=True and the stdout/stderr redirection are otherwise correct.
  • bootstrap.py:156-181 — the model download uses a fixed temp filename with no lock across its four call sites, so two concurrent first-runs truncate each other's file. The pinned SHA-256 usually catches it, but the mismatch message advises pinning the digest of the corrupt file; with verification disabled for a custom model the corrupt file is cached forever. No Content-Length check either, so a cleanly truncated download is promoted.
  • storage.py:41 — if path.exists() and path.is_symlink(): exists() follows symlinks, so a dangling symlink passes the guard that claims to reject symlinks. Harmless today, but strictly weaker than is_symlink() alone.

4. Identity and fingerprinting — two builds can share one vector table

A profile fingerprint that misses something which changes output means incompatible vectors land in the same table. Four such gaps, all verified:

  • Model identity is a path string, never file content partly deferred — see §9 (profiles.py:86 ← embedding_runtime.py:58). resolve_llama_model_path tries the relative path against cwd first, then the data dir — so indexing from the repo and from /tmp resolves to two different GGUF files while producing an identical fingerprint bea283a3f7ce. The runtime fingerprint matches too, so the daemon is not even restarted.
  • ./models/x.gguf and models/x.gguf fork the profile (cli.py:267 vs config.py:399): fingerprints bea283a3f7ce vs d075b69d8f8a. The template cementic config init writes uses the ./ spelling and the code default does not — so accepting the generated config triggers a full re-embed for a path spelling, and bootstrap._model_path_is_default() string-compares too, so the ./ form also silently disables the SHA-256 pin.
  • CHUNKING_VERSION is stale (profiles.py:25). Two commits changed chunk_text output after the last bump (c0c0979 multi-byte boundary fix, 910ae87 empty-slice skip). Collections chunked before c0c0979 hold U+FFFD-corrupted CJK text under a fingerprint byte-identical to today's, and _step_chunk only re-chunks on a content-hash change, so they are never revisited.
  • Extractor identity is a hand-maintained integer (extract.py:131,135). The payload records ExtractorSpec.version = 1, not the pymupdf/pymupdf4llm versions that actually produce the Markdown, and EXTRACTION_VERSION has never been bumped. A dependency upgrade changes the output without moving the fingerprint.

Related: the Nomic prefix marker misses v1/v1.5 (embedding_text.py:28). _NOMIC_V2_MARKER = "nomic-embed-text-v2", so describe_text_policy("models/nomic-embed-text-v1.5.f16.gguf") returns "plain" — but v1.5 needs the same search_document:/search_query: prefixes as v2, and that file is sitting in this repo's own models/. Retrieval quality degrades measurably and silently. The wrong behaviour is currently pinned by tests/unit/test_embedding_text.py:24-26, which asserts it, so it reads as intentional.

7. Docs vs code

Good news first: every command and flag documented in README exists with the exact documented name, and every key in the config init template resolves to a real field. There is no documented-but-unimplemented surface at all.

The drift is in the other direction — 21 live config fields and 4 whole TOML sections are read by config.py but documented nowhere, in neither README nor the annotated template:

  • [llama_cpp] — 10 of 12 fields (n_ctx, n_gpu_layers, embedding_dim, daemon_host/_port, the two timeouts, pid/log files, …). Only model_path and daemon_autostart are documented — and n_ctx is half of §1.
  • [index] — the entire DiskANN tuning group, while README tells users to choose DiskANN and documents all three HNSW knobs.
  • [source_watcher] — the whole section, notably ignore_directories, whose default silently skips 16 directory names including .git, node_modules, build, dist, venv, target. That is user-visible indexing behaviour with an undocumented escape hatch.
  • [pipeline_worker] log/state paths, [bootstrap] model URL and SHA-256.
  • [database] url_override — README documents the env var CEMENTIC_DB_URL, which is the alias; the TOML key name appears nowhere.

Eight CLI flags are also undocumented: --version/-V, status --verbose, status -c, stop --force, chunk --chunk-size/--chunk-overlap, config init --force, init postgres --force.

Two factually wrong architecture claims:

  • README.md:325-326 — "searches only the active revision for the requested collection(s)". False, and README contradicts itself at :179-180. Same overclaim at :111, :157, :5. See §2.9.
  • AGENTS.md:126 — "the only raw SQL is the parameterized vector DDL/KNN in vector_store.py". Raw text() SQL also lives in db.py, doctor.py, pipeline_worker.py, bootstrap.py, collections.py, status_service.py and search.py; and db.py:419, db.py:425 and collections.py:318 interpolate by f-string rather than bind parameters. Smaller: AGENTS.md's file list omits filelock.py and the templates/ tree, and its dependency list still names pgvector (removed per CHANGELOG.md:100) while omitting watchdog, requests and click.
